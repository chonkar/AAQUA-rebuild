## Commands

```bash
npm install            # install deps (postinstall fetches Playwright Chromium)
npm run dev            # Vite dev server (frontend) - default :5173
npm run server         # Express backend on :3001 (loads .env)
npm run start          # production-mode backend (NODE_ENV=production node server/index.js)
npm run build          # production build → dist/
npm run lint           # eslint .
npm run lint:fix       # eslint . --fix
npm run preview        # preview built bundle
npm test               # vitest run — both projects (frontend: jsdom, server: node)
npm run test:e2e       # playwright test (e2e/) — skipped unless E2E_USER + E2E_PASS are set

# Single test file / single project / single test name
npx vitest run tests/server/jobStore.test.js
npx vitest run --project frontend
npx vitest run -t "out-of-range activeStep"

# One-shot Keycloak cutover migration: drops the legacy `users` table and FKs.
# Idempotent (wrapped in BEGIN/COMMIT) — safe to re-run, no-op if already applied.
npm run migrate:cutover   # docker exec into aaqua-postgres + psql

# Local infra: Postgres + Keycloak + Mailpit (SMTP catcher)
docker compose -f docker-compose.security.yml up -d
```

### Tests
`vitest.config.js` defines two projects: **frontend** (`tests/frontend/**/*.test.{js,jsx}`, jsdom, `tests/frontend/setup.js`, Testing Library) and **server** (`tests/server/**/*.test.js`, node, `supertest` against a throwaway `express()` app with `server/middleware/auth.js` replaced via `vi.mock`). Coverage is limited to the Phase 1 primitives (ToolWorkflow, GenerationProgress, SafeHtml, sseClient, llmStream, jobStore, eventRoutes, llmRoutes) — the `server/index.js` monolith and the legacy pages are untested. `e2e/pilot-tools.spec.js` drives a real Keycloak login and is environment-gated: without `E2E_USER`/`E2E_PASS` it reports "skipped" and Playwright doesn't even boot the Vite server (`E2E_BASE_URL`, `E2E_NO_SERVER` override). The E2E user must already own at least one project, or `RequireProject` redirects to `/services`.

`scratch_*.js` and `server/test_cucumber_gen.js` are ad-hoc `node <file>` debug scripts, not part of the suite.

`npm install` runs a `postinstall` hook (`playwright install chromium`) that fetches the Chromium build matching the pinned Playwright version. It's idempotent — no-op if the binary is already cached. Docker image builds bypass this via `npm ci --ignore-scripts`, since the `mcr.microsoft.com/playwright:v1.58.0-jammy` base image already ships matching browsers at `/ms-playwright`.

## Architecture

This is the AAQUA platform: a React + Vite frontend that drives an Express backend. The frontend is a router shell (`src/App.jsx`) over feature pages in `src/pages/`, each backed by a service in `src/services/` that either calls an LLM directly or hits the Express API at `:3001`. The root route `/` is the **Release Readiness dashboard** (the leadership-facing landing page that aggregates automation, accessibility, and localization signals); `/services` is the legacy tool-picker grid (`Home.jsx`).

App-level providers in `App.jsx`: `AuthProvider` (`react-oidc-context`) → `ProjectProvider` (active-project scope) → `ApiTestGenProvider` (sticky API-test-generator workspace state) wrap the `<Router>`. The wrapper `RequireProject` enforces that an active project is selected before a feature page renders (Phase 1: every tool is project-scoped except auth callback, home, and readiness).

### Two-process model
- **Frontend** (`src/`): runs in the browser, talks to LLMs directly through a Vite proxy and to the backend through `/api`.
- **Backend** (`server/`): Express app. `server/index.js` holds feature endpoints (`/api/convert`, `/api/generate-framework`, `/api/parse-spec`, `/api/browser/*`, `/api/scrape`, `/api/analyze-localization`, `/api/analyze-accessibility`, `/api/run-tests*`, `/api/runtime-info`, `/api/heal-*`), with modular routers under `server/routes/` mounted at `/api/projects`, `/api/jira`, `/api/readiness`, `/api/admin/usage`, `/api/mcp`, `/api/testcase-history` (all behind `securityRateLimiter`), plus `/api/recorder` (also aliased at `/api/mcp/recorder`), `/api/events` (SSE) and `/api/llm` (streaming proxy) — mounts are near the bottom of `server/index.js` (~line 3665). `server/agents/` holds LangGraph `StateGraph`s (`testGenAgent`, `autoHealAgent`) imported by `server/index.js` and driven through `llmAdapter.js`; `server/services/emitters/` turns generated API test cases into Playwright / REST Assured / k6 code. Auth tokens are verified against Keycloak (see "Identity" below).
- **Vite proxy** (`vite.config.js`): `/api` → `localhost:3001`, `/llm-api` → `https://llm.lab.aaseya.com` (CORS bypass for browser-side LLM calls).

### Path-prefix routing — `import.meta.env.BASE_URL` is load-bearing
In dev the SPA serves at `/`; in shared-infra QA/prod it serves under `/aaqua/`. The split is driven by Vite's `base` config, which is set from the `VITE_BASE_PATH` build-arg (`vite.config.js` line 5). Five places downstream depend on `import.meta.env.BASE_URL` to construct correct URLs:
- `src/App.jsx` — `<Router basename={BASE_URL.replace(/\/$/, '')}>` so React Router strips the prefix on route match.
- `src/auth/oidcConfig.js` — `redirect_uri = ${origin}${BASE_URL}auth/callback` (without the prefix it collides with shared-Keycloak's `/auth/*` route).
- `src/utils/apiClient.js` — prepends `${API_PREFIX}` to every fetch path.
- `src/utils/llmClient.js` — prefixes the `/llm-api` rewrite.
- `Dockerfile` and `scripts/publish-spa.sh` — pass `VITE_BASE_PATH` as build-arg.

Hardcoded `window.location.href = '/foo'`-style paths bypass React Router's basename and 404 in QA. Always use `<Link to="...">` or `useNavigate()`.

### LLM client — Gemini-shaped wrapper around an OpenAI-compatible endpoint
There are **two near-identical `LocalLLM` classes**: `src/utils/llmClient.js` (browser, rewrites the endpoint to `/llm-api`) and `server/utils/llmClient.js` (server-side, calls the URL directly). Both expose a Gemini-shaped API (`getGenerativeModel({ model }).generateContent(prompt).response.text()`) but POST to an OpenAI-compatible `/chat/completions`. That's why services import it as `import { LocalLLM as GoogleGenerativeAI } from ...` — the alias is intentional, callers were originally written against the Gemini SDK. If you change one client, change both.

Configuration via `.env`: `VITE_LLM_API_KEY`, `VITE_LLM_ENDPOINT` (default `https://llm.lab.aaseya.com/v1`), `VITE_LLM_MODEL` (default `gpt-oss-20b`). The same `VITE_*` vars are read both in the browser (via `import.meta.env`) and on the server (via `process.env` after `dotenv.config()`).

### Database & Modular Service subsystem (beside the monolith)
A modular subsystem that manages persistent domains (Projects, Jira, Release Readiness, automation/accessibility/localization result persistence, MCP agents, TestCase history) with Sequelize + Keycloak-auth conventions. It has its own layered structure under `server/`:

- `models/` — Sequelize models with associations defined in `models/index.js`. Convention: `underscored: true`, `freezeTableName: true`. **No `User` model** — identity is owned by Keycloak; `Project.owner_id` is a plain UUID storing the Keycloak `sub` claim. Current model set:
  - `Project` (project registry).
  - **Per-project result history** (all `Project.hasMany`, `onDelete: CASCADE`): `AutomationResult` (Playwright run summaries), `AccessibilityResult` (axe-core findings), `LocalizationResult` (translation-coverage scans), `ReleaseReadiness` (composite per-dimension scorecards rolled up from the others), `TestCaseHistory` (persisted test case history).
  - Infrastructure models: `Job` (job store / SSE), `AgentRun`, `McpServer`, `McpLocatorLearning`, `UserActivity` (usage dashboard), `TransientDownload`.
- `routes/` — modular routers: `projectRoutes` (→ `/api/projects`), `jiraRoutes` (→ `/api/jira`, fetches Jira stories to seed requirements; per-request Jira creds come in via `x-jira-*` headers, not env), `readinessRoutes` (→ `/api/readiness`, joins the latest result rows across automation/accessibility/localization into a single readiness profile), `mcpRoutes` (→ `/api/mcp`), `testcaseHistoryRoutes` (→ `/api/testcase-history`).
- `services/` — `readinessService` (computes aggregate health score from the per-dimension result tables), `jiraService` (Jira REST client with per-request credentials), `mcpClientService` (MCP tool discovery & execution).
- `middleware/` — `auth.js` (Keycloak JWT verification via `jose` + JWKS — see "Identity" below), `rateLimiter.js`, `urlValidator.js` (SSRF guard).

### Identity — Keycloak owns auth, Express only verifies tokens
Authentication is delegated entirely to Keycloak (realm `aaseya-platform`, OIDC code+PKCE flow). `server/middleware/auth.js` verifies inbound `Authorization: Bearer <jwt>` tokens against Keycloak's JWKS using `jose`, sets `req.user = { id, email, name, roles, raw }` from the token claims, and exposes `requireRole(...allowed)` for role gating. There is **no local password store, no `/auth/login` endpoint, no JWT signing key in `.env`** — all of that lives in Keycloak. The frontend uses `react-oidc-context`; tokens flow via `src/utils/apiClient.js`. The `keycloak` schema is isolated from the app's `public` schema; `server/db.js` pins Sequelize's `search_path` to `public` so `sync({ alter: true })` cannot reach Keycloak's tables.

The legacy local-user model (a `users` table with bcrypted passwords and a `JWT_SECRET`-signed HMAC flow) was retired in the Keycloak cutover. The one-shot migration at `scripts/migrate-drop-users-table.sql` drops the table and its inbound FKs from `projects.owner_id` and `scans.initiated_by`; it's wrapped in `BEGIN/COMMIT` and discovers constraint names at runtime, so it's idempotent — re-running on a cut-over DB is a no-op. Invoke via `npm run migrate:cutover`. If you see code or docs that reference `JWT_SECRET`, `JWT_EXPIRES_IN`, an `authRoutes` module, or a `User` Sequelize model, **the code is stale or wrong** — those have not existed since the cutover.

### Local mail — Mailpit (dev only)
`docker-compose.security.yml` includes a `mailpit` container that catches every email Keycloak sends (verify-email, password reset, etc.) without delivering to a real inbox. SMTP at `mailpit:1025`, web UI at `localhost:8025`. The realm export's `smtpServer` block points at it. **Production uses real SMTP** — configured via the Keycloak admin console (Realm settings → Email), not via the realm JSON. Never include Mailpit in `docker-compose.yml` or `docker-compose.security.prod.yml`.

Boot sequence (bottom of `server/index.js`): `initDatabase()` → `app.listen()`. `initDatabase` runs `sequelize.sync({ alter: true })` so model edits auto-migrate the schema on next start. **DB connection failure is non-fatal** — the server logs a warning and keeps running with persistent database features unavailable; don't add code that assumes the DB is up.

### Database port mismatch — read this
- `docker-compose.security.yml` maps host `5433` → container `5432`.
- `.env` has `DATABASE_URL=...localhost:5433/...` (matches docker-compose).
- `server/db.js` falls back to `localhost:5433` if `DATABASE_URL` is unset.

### Playwright is used two ways
1. As a **library inside the server** (`import { chromium } from 'playwright'`) for the interactive browser endpoints (`/api/browser/launch|capture|close`) and `/api/scrape`, `/api/analyze-localization`, `/api/analyze-accessibility`. `/api/browser/launch` defaults to headless and respects `HEADLESS=false` in `.env` for the local-dev cookie-capture flow. The other endpoints are hardcoded `headless: true`.
2. As a **subprocess test runner** spawned via `child_process.spawn` from `/api/run-tests*` to execute uploaded user test projects. Results are parsed from Playwright's JSON reporter output. Headless is the default; pass `headed: true` in the request body (or `headed=true` form field for the ZIP-upload endpoint) to append `--headed` to the `npx playwright test` argv. This overrides whatever the uploaded `playwright.config.js` sets.

### Headed vs headless: `/api/runtime-info` is the UI gate
`GET /api/runtime-info` (unauthenticated, no secrets) returns `{ hasDisplayServer: !!process.env.DISPLAY, isContainer: existsSync('/.dockerenv'), platform }`. The TestRunner UI hides the "Open browser while running tests" toggle when `hasDisplayServer === false` — there's no point offering a control that crashes in the deployed `mcr.microsoft.com/playwright:v1.58.0-jammy` container (no X11/xvfb). The toggle's last value is sticky per-user via `localStorage` key `aaqua.testrunner.headed`. **Windows devs**: `DISPLAY` is unset by default; set `DISPLAY=1` (any truthy string) in `.env` to force the toggle to appear — Chromium itself works fine on Win32 without an X server, the env var is just our UI heuristic.

### Live log streaming for Playwright runs
Playwright test runs use **cursor-based polling**, not SSE/WebSocket.
- Existing `runStore` Map in `server/index.js` holds a `logs` array capped at 500 chunks via `appendRunLog(run, chunk)`. `GET /api/run-status/:runId?since=<cursor>` returns only the delta. On run completion, the full log is persisted to `temp_runner_logs/<runId>.log` for post-mortem inspection (runs are otherwise ephemeral).

### File-upload flows
`/api/convert` (test framework migration) and `/api/run-tests` accept ZIP uploads via `multer` into `temp_uploads/`, extract with `adm-zip` into `temp_extract/<timestamp>/`, then process. `temp_*` directories are runtime artifacts, not source.

### API Test Generation — OpenAPI spec to runnable suites
A three-step pipeline backed by `@apidevtools/swagger-parser`:
1. `POST /api/parse-spec` accepts an OpenAPI/Swagger spec via JSON URL, raw text, or multipart file upload (with an optional Postman environment file `envFile`) and returns a normalized catalog `{ info, endpoints }` — endpoints are flattened with `{ method, path, pathParams, queryParams, headerParams, requestBodySchema, responses, security }`. An ad-hoc "manual endpoints" mode in `ApiTestGenerator.jsx` (`buildManualCatalog`) lets users assemble the same catalog shape without a spec, so the rest of the pipeline doesn't need to fork.
2. `POST /api/generate-test-cases { endpoints, categories }` — categories are any subset of `['positive', 'negative', 'auth', 'schema', 'boundary']` (defaults: positive + negative + schema). Returns one result row per endpoint with `cases[]`. Errors per endpoint are returned in-line so a single bad spec entry doesn't fail the whole batch.
3. Two downstream materializations off the generated cases: `downloadAutomationProject` (zipped Playwright project), `downloadFlowProject` (multi-endpoint flow with chained state — generated via `generateFlows`), and `downloadLoadTest` (k6 / autocannon script — load-test export of a flow).

The `ApiTestGenProvider` context at app level holds the workspace state (spec, selected endpoints, generated cases, flow definitions) so users can navigate away and come back without losing progress; it does **not** persist across page reloads.

### Release Readiness — aggregate scorecard
`GET /api/readiness/:projectId` joins the latest row per Project from `AutomationResult`, `AccessibilityResult`, and `LocalizationResult` into a single `{ profile, sources }` payload. The UI at `/` renders the per-dimension cards using the raw source numbers (test counts, axe violations, missing localization keys) rather than values derived from the aggregate health score — so a missing dimension shows as "no data" instead of skewing the headline number. `readinessService.getLatestReadiness` returns the most recent `ReleaseReadiness` row (the rolled-up scorecard); `fetchLatestSources` returns the per-dimension raw data.

### Frontend layout
`src/components/common/{Layout,Header,Sidebar}.jsx` provides the chrome; pages render inside `<Layout>`. Styling is per-component inline `<style>` blocks driven by CSS variables (`var(--bg-primary)`, `var(--text-muted)`, etc.) defined in `src/index.css`. There's a `useTheme` hook in `src/hooks/`. No CSS framework, no component library beyond `lucide-react` icons.

## Production deployment — shared-infra model

The committed `docker-compose.yml` is the **AAQUA tenant compose** — only `app` (backend, no nginx). It joins an external docker network `shared-infra_default` (`external: true`) and reads file-mounted secrets from `/opt/shared-infra/secrets/aaqua/`.

The platform tier (Postgres 17, Nginx, Keycloak 24) lives in a separate compose project at `/opt/shared-infra/` on the host. The committed source-of-truth for that stack is `scripts/shared-infra-template/` in this repo; it gets `cp -r`'d to `/opt/shared-infra/` on first deploy. Spec at `docs/superpowers/specs/2026-05-08-shared-infra-deployment-design.md`, executable plan at `docs/superpowers/plans/2026-05-08-shared-infra-deployment.md`.

Tenant routing is path-prefix: `/aaqua/` (SPA), `/aaqua/api/` (backend), `/aaqua/llm-api/` (LLM proxy with Authorization-header injection at the shared edge), `/auth/` (shared Keycloak). The backend code itself is unaware of `/aaqua` — shared-nginx strips the prefix before proxying.

### Deployment gotchas (learned the hard way during the QA box stand-up)
1. **PKCE-S256 needs HTTPS.** Browsers gate `crypto.subtle.digest()` to Secure Contexts (HTTPS or `localhost`). Plain-HTTP deploys silently break the OIDC sign-in with `Crypto.subtle is available only in secure contexts`. The current QA box is `https://aaqua.aaseya.com/aaqua/` (port 443, default HTTPS) with a self-signed cert; production gets a real CA cert. Port 80 is kept open at nginx but does **only** two things: serve `/healthz` (for the container healthcheck — see gotcha #21) and 301-redirect everything else to HTTPS. There's no client-side switch — `oidc-client-ts` mandates S256 for code flow.
2. **`KC_HOSTNAME` must be a bare hostname** (`aaqua.aaseya.com`), NOT a URL (`https://aaqua.aaseya.com:8443`). URL form produces malformed `iss` claims (`https://https//...`) on frontchannel endpoints. **`KC_HOSTNAME_PORT` is conditional**: set it only when serving on a non-default port (e.g. `8443`); when on standard 443, **leave it unset entirely** — setting `KC_HOSTNAME_PORT=443` causes Keycloak to render explicit `:443` in every URL (ugly and not idiomatic). Keep `KC_PUBLIC_BASE_URL` (full URL with scheme + optional port) separate — it's only used by `render-realm.sh` for realm template substitution.
3. **`KC_PROXY_HEADERS=xforwarded` + `KC_HTTP_RELATIVE_PATH=/auth` + `KC_HOSTNAME_STRICT=true` + `KC_HOSTNAME_STRICT_BACKCHANNEL=false`** are the right settings for shared-nginx terminating TLS in front of Keycloak. `KC_PROXY_HEADERS=xforwarded` replaces the deprecated `KC_PROXY=edge` (removed in Keycloak 26+) and matches the `X-Forwarded-Proto`/`X-Forwarded-Host` headers shared-nginx already sets. `STRICT=true` enforces hostname match on frontchannel URLs (login, logout) so a request that arrives via a stale IP or wrong DNS name is rejected; `STRICT_BACKCHANNEL=false` lets the backend reach Keycloak via the docker-internal hostname (`http://shared-keycloak:8080`) for JWKS fetch without tripping the strict check.
4. **Don't use `start --optimized`** in shared-infra's keycloak command. The upstream image is built for H2; with `--optimized` the runtime ignores `KC_DB=postgres` and tries to use H2 to reach a Postgres URL, crashing with `URL format error; must be jdbc:h2:...`. Plain `start` lets Keycloak auto-rebuild for Postgres at boot (~30 s overhead, one-time).
5. **Healthcheck Alpine containers via `127.0.0.1`, not `localhost`.** Alpine's musl libc resolves `localhost` to `::1` first; if nginx isn't listening on IPv6 (it isn't, when we ship our own server block), the healthcheck loops on `Connection refused`.
6. **Shell scripts must have `+x` in the git index.** The official nginx image's entrypoint silently skips non-executable `.envsh` files (`Ignoring <file>, not executable`), then envsubst leaves placeholders unrendered, then nginx emerg-exits on the literal `${VAR}`. Use `git update-index --chmod=+x` from Windows to set the bit.
7. **`.gitattributes` pins shell scripts to LF.** Without it, Windows commits write CRLF, and on Linux `set -o pipefail\r` fails as "invalid option name". Already shipped at the repo root.
8. **AAQUA secrets live ONLY at `/opt/shared-infra/secrets/aaqua/`.** Two consumers — Node-side LLM calls (Docker secret in app container) and the `/aaqua/llm-api/` proxy at shared-nginx (file mount + envsubst). One file, one location, two readers. Copying secrets between dev and QA is forbidden.
9. **Realm import is first-boot-only.** After Keycloak's `keycloak` DB has the realm row, edits to `keycloak/aaseya-platform-realm.template.json` are ignored on restart. Changes after first boot must go through the admin console (or a partial-import) and should be exported back to the template if they're meant to persist across rebuilds.
10. **Self-signed TLS at shared-nginx breaks backend JWKS fetch — split the URL.** When shared-nginx terminates HTTPS with a self-signed cert, the backend's `jose` JWKS fetch throws `Error: self-signed certificate`. But token `iss` claims still carry the public HTTPS URL, so the backend has to (a) match `iss` against the public URL and (b) fetch JWKS via a docker-internal route that doesn't need cert validation. `server/middleware/auth.js` reads `KEYCLOAK_REALM_URL` (public, for issuer match) and an optional `KEYCLOAK_JWKS_URL` (docker-internal HTTP, e.g. `http://shared-keycloak:8080/auth/realms/aaseya-platform/protocol/openid-connect/certs`). If `KEYCLOAK_JWKS_URL` is unset, the code derives it from `KEYCLOAK_REALM_URL` — fine for any deploy where the issuer URL is reachable from the backend without TLS issues. `NODE_TLS_REJECT_UNAUTHORIZED=0` is a faster unblock but disables TLS verification for *all* outbound Node calls (including `llm.lab.aaseya.com`) — prefer the URL split.
11. **DB credentials in the deployed model come from a file-mounted Docker secret.** `docker-compose.yml` sets `DB_HOST=shared-postgres`, `DB_PORT=5432`, `DB_USER=aaqua_app`, `DB_NAME=aaqua_security` and mounts the password at `/run/secrets/db_password` (Compose v2 writes secrets to files, not env vars — the Postgres image's `*_FILE` convention is not universal). `server/db.js` `resolveDatabaseUrl()` builds the connection URL in three-tier precedence: `DATABASE_URL` → `DB_*` env vars + read password from `DB_PASSWORD_FILE` → hardcoded local-dev fallback. DB connection failure remains non-fatal (see "Boot sequence" above) — the server logs a warning and keeps running with persistent database features unavailable.
12. **Realm roles live in the access_token, not the id_token / `profile`.** `oidc-client-ts` exposes `user.profile`, which is the id_token decoded — that does NOT carry `realm_access.roles`. Keycloak puts roles in the access_token. `src/auth/oidcConfig.js` `rolesOf(user)` decodes `user.access_token` directly. If you ever switch to reading from `user.profile.realm_access`, every role gate (e.g. ProtectedRoute admin check) silently fails for every user with a non-blank role list — the symptom is "Forbidden — requires role: admin" for a user who clearly has the role in the token.
13. **Raw `fetch('/api/...')` 404s in QA — the `/aaqua/` prefix is load-bearing.** Always go through `src/utils/apiClient.js` (which prepends `import.meta.env.BASE_URL`) or compute the URL from `BASE_URL` yourself. In dev, relative `/api/...` works via the Vite proxy; in QA shared-nginx only routes `/aaqua/api/...` to the backend — a path without the prefix falls through to nginx's default and returns the canned 404 page. This is especially invisible when the call is a health check that gates a primary action (the button just stays `disabled` and looks unresponsive, with no error surfaced). Canonical pattern: `const API_PREFIX = import.meta.env.BASE_URL.replace(/\/$/, '');` (yields `''` in dev, `/aaqua` in QA), then `fetch(\`${API_PREFIX}/api/foo\`)`. Currently used in `src/utils/apiClient.js`, `src/components/common/Header.jsx`, `src/context/ProjectContext.jsx`, `src/pages/{LocatorGenerator,ReleaseReadiness,TestRunner}.jsx`, `src/services/{autoHeal,testRunner,localization,migration,frameworkGenerator}Service.js`. A future refactor should export `API_PREFIX` once instead of inlining it 10 times.

14. **GCP provisioning is a two-script pattern**: `scripts/gcp-provision.sh` runs on your workstation (`gcloud` + auth required) and creates the VM, static IP, firewall rules, and DNS-ready public IP. `scripts/gcp-vm-startup.sh` is the cloud-init script attached as `startup-script` metadata — it runs ONCE on first boot as root, installs Docker, clones the repo to `/opt/aaqua`, and seeds `/opt/shared-infra/` from `scripts/shared-infra-template/`. **The repo has `qa-test-gen/` as a subdirectory**, but `onboard-aaqua.sh` defaults to `AAQUA_REPO=/opt/aaqua` and then does `cd $AAQUA && bash scripts/publish-spa.sh`, which 404s because the scripts live at `/opt/aaqua/qa-test-gen/scripts/`. Always invoke onboarding with `AAQUA_REPO=/opt/aaqua/qa-test-gen` overridden.

15. **`gcp-vm-startup.sh` pre-creates the `shared-infra_default` docker network** so the tenant compose can come up first. Side effect: when the *shared-infra* compose (which declares the network as a normal Compose-managed network, not `external: true`) runs first, it sees an existing network without Compose's labels and refuses to adopt it (`network shared-infra_default was found but has incorrect label`). One-time workaround on first bring-up: `docker network rm shared-infra_default` before `docker compose up` in `/opt/shared-infra/`. Compose then creates it with proper labels and the tenant compose joins it via `external: true`. Long-term fix: mark the network `external: true` in `scripts/shared-infra-template/docker-compose.yml`.

16. **`onboard-aaqua.sh` is tenant-scoped, NOT platform-scoped.** It writes only the tenant secrets (`secrets/aaqua/db_password.txt`, `secrets/aaqua/llm_api_key.txt`) and renders the realm template. It does NOT create `/opt/shared-infra/.env` (with `KEYCLOAK_ADMIN_PASSWORD`, `KEYCLOAK_DB_PASSWORD`, `KC_HOSTNAME`, `KC_PUBLIC_BASE_URL`) or `secrets/postgres_super_password.txt` — without those, `docker compose up` fails with `KEYCLOAK_DB_PASSWORD: set in .env`. The platform-scoped secrets must be generated separately (`openssl rand -base64 32`) and `/opt/shared-infra/.env` populated from `.env.example` before bringing up the shared-infra stack.

17. **`shared-nginx` resolves upstream hostnames at config-load time, not request time.** If `aaqua-app` isn't on the shared docker network when nginx parses `proxy_pass http://aaqua-app:3001/...`, nginx emerg-exits with `host not found in upstream` and enters a restart loop. Workarounds in order of preference: (a) bring the AAQUA tenant compose up alongside or *before* shared-nginx so `aaqua-app` is resolvable; (b) refactor the tenant nginx template to dynamic resolution: `resolver 127.0.0.11 valid=10s; set $up aaqua-app; proxy_pass http://$up:3001/...` — Docker's embedded DNS at `127.0.0.11` resolves at request time, so nginx starts even with the upstream missing and only 502s on actual requests. Option (b) is the long-term fix; option (a) unblocks today.

18. **`gcloud compute ssh` on Windows: stdin piping is unreliable.** `printf '%s' 'key' | gcloud compute ssh ... --command='sudo tee file'` truncated a 25-byte key down to 2 bytes — plink's TTY handshake on Windows eats the first bytes when stdin isn't a real terminal. Two reliable approaches: (a) inline the literal value into `--command` itself (the SSH protocol passes the whole command string verbatim); (b) `gcloud compute scp` (uses pscp on Windows, which is binary-safe). Use (b) for any non-trivial secret transfer.

19. **`gcloud compute ssh` long-running scripts need `nohup` to survive SSH disconnects.** A foreground `sudo bash script.sh` over SSH dies if SSH disconnects mid-run (SIGHUP propagates through the process group). For scripts that run 30+ seconds — SPA rebuilds, keycloak healthcheck waits, migration scripts — use `sudo nohup bash /tmp/script.sh </dev/null >/dev/null 2>&1 &` and have the script log internally via `exec > >(tee -a /var/log/foo.log) 2>&1`. Poll the log file from subsequent SSH calls to track progress.

20. **Keycloak realm reset requires dropping the Postgres `keycloak` database.** `--import-realm` only runs when the realm doesn't already exist in the DB — once the row is there, edits to `keycloak/aaseya-platform-realm.template.json` (re-rendered or not) are ignored on restart. To force a re-import (e.g. after changing `PUBLIC_BASE_URL` for a port migration): `docker compose stop keycloak`, then `docker exec shared-postgres psql -U postgres -c "DROP DATABASE IF EXISTS keycloak; CREATE DATABASE keycloak OWNER keycloak_user;"`, then `docker compose up -d keycloak`. The master admin user gets re-created from `KEYCLOAK_ADMIN_PASSWORD` env on next first-boot, so the admin password from `.env` is restored automatically. Destructive — wipes any admin-console edits made since the last realm import.

21. **HTTP→HTTPS redirect at nginx must exempt the container healthcheck path.** The official nginx image's healthcheck is `wget -qO- http://127.0.0.1/healthz`. With `return 301 https://$host$request_uri` on port 80, the wget follows the redirect to `https://127.0.0.1/healthz` — and since the cert is for `aaqua.aaseya.com` (not `127.0.0.1`), TLS verification fails, wget exits non-zero, Compose marks nginx unhealthy, restart loop. Keep `/healthz` answering 200 directly on port 80, redirect everything else. The port 80 listener also stays useful for future Let's Encrypt HTTP-01 challenges.

22. **Keycloak's `Set-Cookie` headers exceed nginx default proxy buffers.** Default `proxy_buffer_size` is 4 KB; Keycloak's `AUTH_SESSION_ID` + `KC_RESTART` + `KEYCLOAK_LOCALE` plus standard headers easily exceed it. Symptom: intermittent 502 `upstream sent too big header while reading response header from upstream` on `/auth/realms/.../auth` during sign-in. Fix in the `location /auth/ { ... }` block: `proxy_buffer_size 16k; proxy_buffers 4 16k; proxy_busy_buffers_size 32k;`.

23. **The repo template is the source of truth — inline edits on `/opt/shared-infra/` get clobbered on the next redeploy.** `scripts/gcp-vm-startup.sh` (cloud-init) and `scripts/publish-spa.sh` both seed `/opt/shared-infra/` from `scripts/shared-infra-template/`. Any ops-time fix applied directly to `/opt/shared-infra/nginx/conf.d/*.conf`, `docker-compose.yml`, or the secrets/realm templates that is NOT backported to the repo template WILL be reverted on next deploy. The 2026-06-17 incident exhibited the full failure mode: a previous HTTPS rollout had added the entire `server { listen 443 ssl; ... }` block (plus gotcha #21 healthz exemption and gotcha #22 buffer-size tuning) directly on the QA box; redeploy seeded from the older template; `:443` lost its listener; `https://aaqua.aaseya.com/` returned "Connection refused after 1ms" because docker-proxy was bound but no nginx listener was behind it. The compose comment `# nginx: public edge on :80 (later :443)` is the half-finished marker that exposed the gap — grep `(later)`, `TODO`, `FIXME` in `scripts/shared-infra-template/` before every redeploy. **Workflow rule**: ANY edit to `/opt/shared-infra/` MUST have a matching commit in `scripts/shared-infra-template/` before the SSH session ends.

24. **GitLab CI auto-deploy: runner on the VM, shell executor, dedicated `gitlab-runner` user.** Push to `main` on `git.lab.aaseya.com/camunda/aaqua` triggers the `.gitlab-ci.yml` job tagged `aaqua-deploy`. That job is picked up by a runner installed on `aaqua-host` itself via `scripts/install-gitlab-runner.sh`. The runner runs as the `gitlab-runner` system user (added to `docker` group, no sudo), with `/opt/aaqua` and `/opt/shared-infra/nginx/sites/aaqua/` chowned to it. The rest of `/opt/shared-infra/` stays root-owned — privileged file ops in CI go through Docker containers (see `.gitlab-ci.yml`: `docker run --rm -v /opt/shared-infra:/mnt/shared-infra alpine cp ...`). **No PAT lives on the VM** — CI fetches the repo using `CI_JOB_TOKEN`, a short-lived per-job credential GitLab injects automatically. `concurrent = 1` because `publish-spa.sh` does `rm -rf $TARGET/...` before `docker cp` — two parallel deploys would race on `/opt/shared-infra/nginx/sites/aaqua/`. **GitLab Runner 16+ auth-token model: the UI form is the source of truth, not the CLI flags.** When you click "New project runner" in the GitLab UI, the form's Tags / Run-untagged / Lock-to-project / Protected fields are stored server-side bound to the auth token GitLab mints (`glrt-...`). The CLI `gitlab-runner register --tag-list ... --locked --run-untagged=false` flags are SILENTLY IGNORED if you pass the new-style token via the legacy `--registration-token` flag — GitLab emits a warning ("legacy-compatible registration process — the following command line parameters being ignored: --locked, --access-level, --run-untagged, --tag-list, ...") and falls back. **Symptom**: runner registers, shows online, stays idle because server-side tags are blank (UI form's Tags field was empty or had a typo). **Fix in install-gitlab-runner.sh**: detect flag by token prefix (`glrt-*` → `--token`, else → `--registration-token`); also fill in the UI form's Tags field as `aaqua-deploy` **before** clicking Create. *(Observed 2026-10-16 on the AWS host: the script still took the legacy path with a `glrt-` token, so treat the UI Tags field as the only source of truth — see AWS gotcha #3.)* To rotate the runner (compromise, decommission, machine swap): in the GitLab UI go to Project → Settings → CI/CD → Runners → delete the entry, then on the VM run `sudo gitlab-runner unregister --name "aaqua-host shell deploy"` (the surgical equivalent — leaves any unrelated runners on the host alone, unlike deleting the whole `config.toml`), then re-run `install-gitlab-runner.sh` with a fresh token. `gcp-vm-startup.sh` auto-installs the runner if VM metadata `aaqua-gitlab-runner-token` is set, so newly-provisioned VMs come up CI-ready. Path consistency: the repo clones to `/opt/aaqua` (matching gotcha #14's `AAQUA_REPO=/opt/aaqua/qa-test-gen` override), and `.gitlab-ci.yml` `DEPLOY_ROOT` matches this — if a CI job dies with `cd: /opt/aaqua/repo: No such file`, the YAML drifted to an older path and the fix is the one-line `DEPLOY_ROOT` correction. Docker secrets referenced in `docker-compose.yml` (`llm_api_key`, `db_password`, `jira_token`) must ALL live at `/opt/shared-infra/secrets/aaqua/<name>.txt` per gotcha #8 — empty placeholder files are fine for disabled features (e.g. `jira_token.txt` is empty when `JIRA_ENABLED=false`). The 2026-06-17 first-auto-deploy incident failed twice on `bind source path does not exist` for `jira_token.txt` because the secret originally used a relative `./secrets/...` path that drifted from this convention.

25. **`/opt/aaqua/qa-test-gen/.env` on the VM is CI-owned and silently shadows the compose defaults.** The `.env` file at `/opt/aaqua/qa-test-gen/.env` is owned by `gitlab-runner` and (re)generated by CI from GitLab **Project → Settings → CI/CD → Variables**. Docker Compose's `${VAR:-default}` syntax uses the default ONLY when the variable is unset or empty — a `.env` line like `KEYCLOAK_REALM_URL=https://aaqua.aaseya.com/...` will win over the repo's `docker-compose.yml` default even if the default was updated in a recent commit. On 2026-07-15 this masked the URL migration completely: `docker-compose.yml` on the VM had the new IP-based default, git log showed the commit deployed, but `docker exec aaqua-app env` returned the old domain URL because CI had generated `.env` from stale variables. **Fix**: either update the GitLab CI/CD variables to the new value, or delete them entirely so the compose default takes effect. If you edit `.env` on the VM directly, the next CI run WILL overwrite it — always fix the source (GitLab variables).

26. **`docker restart` does not re-read env vars — use `docker compose up -d --force-recreate`.** Container env vars are captured at container CREATE time, not at container START time. So after editing `.env`, `docker restart aaqua-app` starts the SAME container with the SAME frozen env — your changes are invisible. `docker compose up -d` normally detects the env change and recreates; `docker compose up -d --force-recreate <service>` guarantees a rebuild regardless. Symptom: you edit `.env`, restart, `docker exec app env` still shows the old value; you scratch your head for 10 minutes. This is a subtle Docker foot-gun that eats time from experienced operators.

27. **`publish-spa.sh` must run as `gitlab-runner`, not root — `sudo bash publish-spa.sh` breaks the next CI deploy.** Per gotcha #24, `/opt/shared-infra/nginx/sites/aaqua/` is chowned to `gitlab-runner` specifically so CI can manage it (`publish-spa.sh` does `rm -rf $TARGET/assets` before `docker cp`ing the new bundle). If you manually run the script with plain `sudo` during debugging, the newly-published files become root-owned; the next CI run (as `gitlab-runner`) then hits `rm: Permission denied` and the pipeline fails. **Correct manual invocation**: `sudo -u gitlab-runner bash /opt/aaqua/qa-test-gen/scripts/publish-spa.sh`. **Recovery after the fact**: `sudo chown -R gitlab-runner:gitlab-runner /opt/shared-infra/nginx/sites/aaqua/` then re-trigger the pipeline.

28. **PostgreSQL `DROP DATABASE` cannot run inside a transaction — split into separate `psql -c` calls.** `psql -c "DROP DATABASE IF EXISTS keycloak; CREATE DATABASE keycloak OWNER keycloak_user"` fails with `ERROR: DROP DATABASE cannot run inside a transaction block` because psql wraps multi-statement `-c` invocations in an implicit transaction. Same restriction applies to `CREATE DATABASE`, `VACUUM`, and a few other DDL commands. **Correct form**: two separate calls, each with a single statement:
    ```bash
    docker exec shared-postgres psql -U postgres -c "DROP DATABASE IF EXISTS keycloak"
    docker exec shared-postgres psql -U postgres -c "CREATE DATABASE keycloak OWNER keycloak_user"
    ```
    **CRITICAL corollary — dump before dropping.** PostgreSQL has NO undo for DROP DATABASE; the tablespace files are unlinked immediately. On 2026-07-15 the Keycloak DB was dropped during a debugging retry and every user (~50 accounts) was lost, unrecoverable because no WAL archive / no `pg_dump` / no GCP snapshot existed. Always `pg_dump` before ANY destructive Postgres operation on production or QA:
    ```bash
    docker exec shared-postgres pg_dump -U postgres keycloak > /tmp/keycloak-$(date +%s).sql
    ```

### Bulk user import via CSV
For recovery-after-data-loss or onboarding a team of testers, the repo ships a CSV-driven bulk-import tool: `scripts/users-template.csv` (columns: `username,email,fullName,temporaryPassword,realmRoles`) and `scripts/import-users.sh`. The script authenticates as the Keycloak master admin (`KC_ADMIN_PW` env var), iterates CSV rows, creates or updates each user in `aaseya-platform`, sets `--temporary` passwords (Keycloak forces change on first login), and assigns realm roles (`;`-separated for multiple). `fullName` is split on the first space to populate Keycloak's separate `firstName` / `lastName` (Keycloak has no native single-name field). Usage on the VM: `export KC_ADMIN_PW='<from /opt/shared-infra/.env>'; ./scripts/import-users.sh /tmp/users.csv`. **CSV parsing note**: uses `IFS=,` which is not full RFC 4180 — names with embedded commas or quotes will break rows; for typical `First Last` names it's fine. **Usernames must be lowercase and non-empty** — see AWS gotcha #8 below. To run it on a host where the repo is owned by `gitlab-runner`, copy the CSV to `/tmp` and read the password on the host: `export KC_ADMIN_PW="$(sudo grep '^KEYCLOAK_ADMIN_PASSWORD=' /opt/shared-infra/.env | cut -d= -f2)"`.

## Conventions worth noting

- ESM throughout (`"type": "module"` in `package.json`). Server uses `import` syntax with explicit `.js` extensions.
- ESLint rule `no-unused-vars` ignores names matching `^[A-Z_]` — uppercase identifiers can be left unused.
- `.env` is **gitignored and untracked** as of commit `f69bd7e`. The committed `.env.example` is the safe template — never commit a populated `.env`. The repo's local `.env` may contain real secrets (`VITE_LLM_API_KEY`, `KEYCLOAK_ADMIN_PASSWORD`, `KEYCLOAK_DB_PASSWORD`); don't print them in transcripts or PRs, don't commit replacements that would invalidate live values. There is **no JWT secret** anywhere — token verification uses Keycloak's public JWKS, not a shared HMAC.

## UI architecture (Phase 1)

Phase 1 introduced an MUI foundation and a small set of shared primitives that new/migrated tool pages are expected to build on, plus job-store + SSE infrastructure so long-running LLM generations stream progress instead of blocking on a single request/response.

- **Theme**: `getTheme(mode)` in `src/theme.js` builds the MUI theme from brand tokens mirrored off `src/index.css`. `ThemeProvider` + `CssBaseline` + `NotificationProvider` are wired in `src/App.jsx`, with dark/light `mode` state lifted to `App` (via `useTheme` in `src/hooks/`) so the MUI theme and the legacy CSS-variable toggle (`data-theme` attribute, still driving un-migrated pages' inline `<style>` blocks) share one source of truth instead of drifting apart.
- **Notifications**: `useNotify()` (from `NotificationProvider`, `src/components/common/NotificationProvider.jsx`) returns `{ success, error, info, ... }` snackbar helpers — the standard way to surface async results instead of ad-hoc `alert()`/console logging.
- **ToolWorkflow** (`src/components/workflow/ToolWorkflow.jsx`) — locked stepper-frame contract, fully controlled by the caller: props `title`, `steps: [{ key, label, content, canAdvance }]`, `activeStep`, `onStepChange`. Step `content` unmounts on navigation, so all page state must live in the hosting page component, not inside a step's own subtree (see "Every piece of user-visible state lives here" comment in `TestGenerator.jsx`). `canAdvance` disables Next only when it is strictly `false` (omitting it, or any other value, leaves Next enabled). An out-of-range `activeStep` is clamped rather than crashing. `autoAdvanceWhen` is a reserved field in the step shape, currently unconsumed — a future step type could request the frame auto-advance without the page wiring `onStepChange` itself.
- **GenerationProgress** (`src/components/workflow/GenerationProgress.jsx`) — props `{ jobId, streamText, onDone, onRetry }`. Two combinable modes: pass `jobId` to subscribe to backend job progress over SSE, or pass `streamText` for a page that's accumulating its own LLM stream text (the pilots use this mode). Progress is monotonic (never regresses once shown) and internal state resets whenever `jobId` changes. `onRetry` is expected to start an entirely new job/stream, not resume the old one.
- **SSE**: `subscribeToJob(jobId, handlers)` (`src/utils/sseClient.js`) talks to `GET /api/events/:jobId` (`server/routes/eventRoutes.js`, mounted at `/api/events` in `server/index.js`). Because `EventSource` cannot set headers, the access token travels as a `?access_token=` query param — be aware this lands in edge/proxy access logs, unlike the `Authorization: Bearer` header used everywhere else. The route verifies the token itself (can't reuse the standard `authenticateToken` middleware for the same header-vs-query reason), checks `job.owner_id` against the caller (jobs with no `owner_id` are system jobs, readable by anyone authenticated), replays already-emitted progress on connect (so a client that subscribes late or reconnects doesn't miss history), and sends a `: ping` heartbeat on an interval to keep the connection alive through idle proxies.
- **Job store**: `server/services/jobStore.js` — `createJob({ type, ownerId, payload })`, `updateProgress(id, { progress, phase })`, `completeJob(id, result)`, `failJob(id, err)`, `getJob(id)`, plus a module-level `jobEvents` EventEmitter that `eventRoutes` subscribes to for live updates. Terminal-state guarded (a completed/failed job ignores further progress updates). **Contract is deliberately split by caller**: `createJob`/`getJob` throw on DB failure (a request handler that can't create or find its own job has nothing sensible to return), while `updateProgress`/`completeJob`/`failJob` swallow DB errors and resolve to `null` (a background runner mid-generation shouldn't crash because a progress-write to Postgres failed transiently — it should keep generating and let the next write retry).
- **LLM streaming proxy**: `streamLLM({ prompt, maxTokens, temperature, reasoningEffort, onToken, signal })` (`src/utils/llmStream.js`) POSTs to `/api/llm/generate`, which relays the upstream OpenAI-compatible SSE stream verbatim (`server/routes/llmRoutes.js`). This is now the **only** path pilot pages use to reach the LLM — zero direct browser→LLM-gateway calls in migrated services (contrast with the pre-Phase-1 pattern of instantiating `LocalLLM` straight from the browser). `reasoningEffort: 'low'` matters for `gpt-oss` models specifically: without it, a reasoning model can spend its entire token budget "thinking" and return empty content instead of an answer.
- **SafeHtml** (`src/components/common/SafeHtml.jsx`) — the only sanctioned way to render HTML this app didn't author itself (LLM completions, JIRA descriptions, scraped pages — all attacker-reachable). Wraps DOMPurify's `html` profile. **Never use `dangerouslySetInnerHTML` directly.** Sanitize at render time only — exporters (e.g. `html-docx-js`) need the original unsanitized markup (DOMPurify's profile strips `<style>` blocks a .docx converter needs), and a generated document isn't a browser execution context anyway.
- **THE RULE**: new or migrated tool pages must be built on these primitives (ToolWorkflow + GenerationProgress + streamLLM/SSE + SafeHtml for any rendered untrusted HTML), not the pre-Phase-1 ad-hoc patterns. `src/pages/TestGenerator.jsx` and `src/pages/TestPlanGenerator.jsx` are the reference implementations — copy their shape (page owns all state, `STEP_ORDER` array as the single source of truth for step index, `AbortController` for cancel) rather than reinventing it per page.

**Known Phase 2 debt** (called out here so it doesn't get rediscovered from scratch):
- JIRA-story-import UI is duplicated between the two pilot pages (`RequirementInput`'s JIRA tab equivalent). Extract a shared `JiraStoryImport` component before the next JIRA-consuming page migrates.
- The `jobs` table has no pruning job and no indexes beyond the primary key — fine at Phase 1 volumes, will need attention once job history accumulates.
- Two services still call the LLM gateway directly from the browser via the legacy `LocalLLM`/`GoogleGenerativeAI` client (`src/utils/llmClient.js`): `src/services/locatorGenerationService.js` and `src/services/testDataService.js`. (`testCaseGenerationService.js` and `testPlanService.js` only mention `llmClient.js` in explanatory comments — both are already fully migrated to `streamLLM`.)
- `TestRunner` and the scanner pages (`AccessibilityScanner`, `LocalizationTester`) still use cursor-based polling for long-running operations rather than the job-store/SSE mechanism introduced in Phase 1 — converting them is Phase 2 scope.
- Pre-existing lint errors (`react-hooks/set-state-in-effect`, plus an `exhaustive-deps` warning) remain in unmigrated code: `src/context/ProjectContext.jsx`, `src/pages/ReleaseReadiness.jsx`, `src/pages/UsageDashboard.jsx`. These predate Phase 1 and are out of scope here — fixing them means touching pages that haven't been migrated to the new primitives yet.
